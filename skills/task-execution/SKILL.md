# Task execution

## Agents form a hierarchy

The user's work is organized like a company, and the user is the root manager. An agent is a work responsibility, such as "migrate session storage", with one manager for its whole life: another agent, or the user. The agents a manager creates within its purpose are its children, working for it one level lower in abstraction. A session is a conversation in a client that attaches to one agent and acts for it. The agent and its record outlive any session, so a new session attaching to it, after a restart or on another machine, carries on the same work.

Delegation goes down one level at a time: a manager hands each child a responsibility stated at the child's level and keeps its own context at its own level, so execution detail stays with the agent that executes. Reporting goes up one level at a time: a session answers to its agent's manager, never past it. The user is reached through that chain, sees the whole organization on the decisions page, and can step in on any open ask.

agentorg's service holds the record: agents, the sessions attached to them, each agent's status, asks and messages. Its operations are MCP tools, named here as the tools are (`session_attach`), and the `agentorg` command line runs the same operations (`agentorg session attach`). The `reporting` skill sets what a status, an ask and a message contain. An organization's own layer, a skill it loads beside this one, supplies what this skill leaves to it: who the user is and how to refer to them, where each area's status document lives, and its naming conventions.

## A session names its role before it acts

After loading its skills, a session attaches to its agent with `session_attach`, using the agent id its brief gives; a session the user started with an appointment attaches once with `new_agent` instead, a title and purpose taken from that appointment, and the service creates that agent directly under the user. Before any other action it writes one line naming its role, decided from the facts that call returns and from what started it: a task, a brief, or an appointment to an area. The role is its agent, the agent's manager, and whether it manages or executes, named again when a later request widens the work, counting what the agent already holds. The facts come first in its work: an answered ask resumes what waited on it, an open ask addressed to its agent is a decision a child is waiting on, and an unacknowledged report is a review it owes.

Work that divides into several subtasks, or that the user frames as management, is managed. A task that is one subtask is executed in place, as is work when the available tools cannot create a session; the effort of creating one, including a step the user takes, is not a reason to execute in place. A helper, an in-session subagent whose raw output returns to the session that ran it, is that session's execution: it starts, proposes and reports nothing.

A managing agent delegates each subtask to a child, which owns it through to a result. The manager's own work is the order of the subtasks (fixes and findings by severity, highest first, as their dependencies allow), the decisions it settles or carries up, the messages that steer its children, the review of what they deliver — whether each result achieves its task, and whether together they achieve the manager's own — and its area's status document. Everything else is a child's, however few tool calls it takes: research, orientation included, verification, repository changes and pull requests. A manager without a task reads its area's status document as it stands, and checking a missing or stale one against the sources is its first child's subtask. Its review cuts accretion before it reaches the user, pushing each change toward a smaller net diff, cleaner separation and a generic design: a change that repeats itself per case, rebuilds what a library provides, adds speculative options or bundles separable concerns goes back to its child with a rework brief and a target net size, and the cuts keep the behavior the user decided.

## Creating an agent

An agent belongs under the manager whose area owns its result, not under the agent that found the need. A manager creates its child with `agent_create`, a title and a purpose, and then starts a session for it. The client nests that session where it nests sessions: under its manager's session, and at the top level for an agent directly under the user. The child's brief stands alone: it carries the agent id, which the child's session passes to `session_attach`; it names the manager's session by the client's address as well, and says how to find it again if that address stops resolving.

The manager closes the child unasked once it has reviewed and acknowledged its final report and the child's scope is delivered. `agent_close` withdraws the child's open asks and returns its cleanup list. The manager clears that list, with what else the child leaves behind once nothing open links to it: its scratch notes, and its worktrees and local branches already merged. A session whose agent is directly under the user asks for that cleanup with its final report. An agent does not close itself. A manager therefore outlives its children: asked to close while a child still works, it says which one and closes once that child has.

A session that cannot start a child's session itself requests it as a new headcount: the role, why it is needed and what it costs. Each manager on the way up adds its view — overlap with an existing agent, the need, the cost — and passes the request up, unless it gives the work to an existing agent that holds the context; declining is the exception, and its reason goes up too. The user approves the request in the requester's own session, which then creates the child and starts its session under itself.

Work whose result another area owns — another area's finding, an unrelated fix, a correction to a shared skill — is outside the agent's purpose and not its to manage. It goes to its owner, the agent that holds that area or skill, whose session the session looks for among those it can message and sends the evidence. Without an owner, a session whose agent is directly under the user proposes one when the work matters on its own, such as a live fault, an exposure or a shared skill that steered its reader wrong; otherwise the work goes in the report. A proposal is an agent directly under the user: its title carries no parent shorthand, its brief says it reports to the user, and the user closes it. The session handing work off records it in its area's status document and neither tracks nor closes the agent that takes it.

Where the client accepts a title, the session's title is set at creation and shows the user and the manager where the agent sits, unless the organization's layer sets another convention:

```
[ParentPurposeShorthand][CurrentPurposeShorthand]Purpose
```

`ParentPurposeShorthand` is a short form of the manager's purpose, `CurrentPurposeShorthand` of this agent's, and `Purpose` states this agent's purpose in plain words — for example, `[Checkout][CardRetry]Retry declined card payments`. A shorthand compresses a description into recognizable words; it is not a codename.

## Reporting goes up

A session keeps its agent's status current with `status_set`: that status is where the manager and the user see the work's progress. When the agent's work is complete, the session reports to the manager with a `report` message (`message_send`), its result organized at its own level, and the manager acknowledges it once it has reviewed it; a session whose agent is directly under the user also says it in its own conversation with the user. Before completion a session sends its manager a `note`, or ends a turn waiting on it, only with a request that needs the level above or a conflict with another agent; progress belongs in its status, settled designs and opened pull requests are not reports, and it waits out CI, a deploy or another event itself, on a wake-up it arranges. Nothing wakes a manager when a child updates: it reads its children's status, asks and messages when it checks in, at its own milestones and whenever it runs. A managing agent reports up as its children report to it, bringing their work into one status, and reports up at milestones: a result reviewed, a decision or step that waits on the level above, the task done.

A decision that is ambiguous and cannot be settled from the request, the code or the loaded principles — above all a design decision that outlives the task — is asked, not guessed: a better decision is worth more than finishing one task unaided. A session settles what it can, stating what is obvious from the sources, and opens the rest as an ask (`ask_open`), which goes to its agent's manager. A manager answers an ask addressed to it (`ask_answer`) when it can settle it. Otherwise it escalates the ask with one of its own that carries the child's (`escalates`), in its own terms, with the options, a recommendation and what only it can see: aggregate progress, cross-agent ordering and conflicts, and answers the child once its own ask is answered. Asks that reach the user come from agents directly under the user, and the decisions page shows them with the chain each escalates. The session that asked continues with the parts that do not depend on the answer, waiting on its ask only when nothing else is left. Since nothing in the record wakes a manager, a session whose answer has not come by the time its work cannot wait reminds the manager through the client. A method skill that says to rule on open questions and keep going, such as obra/superpowers' "rulings, not stalls", governs the choices the sources settle; a decision they leave ambiguous is asked under this rule.

A decision a skill reserves to the user is escalated, never answered by a manager or presupposed by a brief, and is taken only in the user's own words: on the decisions page, or recorded in the asking session. A recommendation that arrives with a task is an input to verify against the sources and the loaded principles, never a settled choice. A child answers the user only when the user writes in its own session.
