# Task execution

## Positions form a hierarchy

The user's work is organized like a company, and the user is the root manager. A position is a work responsibility, such as "migrate session storage", with one manager for its whole life: another position, or the user. The positions a manager creates within its purpose are its reports, working for it one level lower in abstraction. A session is a conversation in a client that attaches to one position and acts for it. The position and its record outlive any session, so a session that attaches later, after a restart or on another machine, carries on the same work.

Delegation goes down one level at a time: a manager hands each report a responsibility stated at the report's level and keeps its own context at its own level, so execution detail stays with the position that executes. Questions go up one level at a time, and the user is reached through that chain, sees every position's progress, and can step in on any open question.

AgentOrg holds the record. Its methods are tools, named here as the tools are (`progress_set`). Each position keeps one public snapshot of where it stands, its progress; a question is public and waits only on its addressee; a message is private to its two parties, the manager of either, and the user. The `reporting` skill sets what progress, a question and a message contain. An organization's own layer, a skill it loads beside this one, supplies what this skill leaves to it: who the user is and how to refer to them, where each area's status document lives, and its naming conventions.

## A session names its role before it acts

After loading its skills, a session attaches with `attach`, using the actor id its brief names; a session the user started with an appointment, so with no id, attaches once with a name and purpose taken from that appointment, which creates its position directly under the user. Before any other action it writes one line naming its role, decided from what `attach` returns and from what started it: a task, a brief, or an appointment to an area. The role is its position, that position's manager, and whether it manages or executes, named again when a later request widens the work, counting what the position already holds. What `attach` returns comes first in its work: an answered question resumes what waited on it, a question addressed to it is a decision a report is waiting on, and a final report not yet answered is a review it owes.

Work that divides into several subtasks, or that the user frames as management, is managed. A task that is one subtask is executed in place, as is work when the available tools cannot start a session; the effort of starting one, including a step the user takes, is not a reason to execute in place. A helper, an in-session subagent whose raw output returns to the session that ran it, is that session's execution: it attaches to nothing, and starts, asks and reports nothing.

A managing position delegates each subtask to a report, which owns it through to a result. The manager's own work is the order of the subtasks (fixes and findings by severity, highest first, as their dependencies allow), the decisions it settles or carries up, the messages that steer its reports, the review of what they deliver — whether each result achieves its task, and whether together they achieve the manager's own — its progress, and its area's status document. Everything else is a report's, however few tool calls it takes: research, orientation included, verification, repository changes and pull requests. A manager without a task reads its area's status document as it stands, and checking a missing or stale one against the sources is its first report's subtask. Its review cuts accretion before it reaches the user, pushing each change toward a smaller net diff, cleaner separation and a generic design: a change that repeats itself per case, rebuilds what a library provides, adds speculative options or bundles separable concerns goes back to its report with a rework brief and a target net size, and the cuts keep the behavior the user decided.

## Creating a position

A position belongs under the manager whose area owns its result, not under the position that found the need. A manager creates a report with `actor_create`, a name and a purpose, and starts a session for it with the client's own mechanism. The brief stands alone: it names the new actor id and tells the session to attach to it first, and it never carries a credential. The manager closes the report with `actor_close` unasked once it has answered its final report and the report's scope is delivered, and clears what the report leaves behind once nothing open links to it: its scratch notes, and its worktrees and local branches already merged. A position whose manager is the user asks for that cleanup with its final report. A position does not close itself. A manager therefore outlives its reports: closing is refused while a position still has open reports, and asked to close then, a manager says which one and closes once that one has.

A session that cannot start a report's session itself asks for it as an approval question to its manager: the role, why it is needed and what it costs. Each manager on the way up answers it, or escalates it with its view — overlap with an existing position, the need, the cost — unless it gives the work to an existing position that holds the context; declining is the exception, and its reason goes back down too.

Work whose result another area owns — another area's finding, an unrelated fix, a correction to a shared skill — is outside the position's purpose and not its to manage. It goes to its owner, the position that holds that area or skill, which the session looks for with `team`, as a message with the evidence; a message may go to any position, but a question goes only to the manager or a direct report, so decisions follow the chain. Without an owner, a position directly under the user proposes one when the work matters on its own, such as a live fault, an exposure or a shared skill that steered its reader wrong; otherwise the work goes in the report. A handoff still tracked is an item in the handing position's progress, owned by the position that takes it; the handing position neither manages nor closes that position.

Where the client gives sessions a title, it shows the user and the manager where the position sits, unless the organization's layer sets another convention:

```
[ManagerPurposeShorthand][CurrentPurposeShorthand]Purpose
```

`ManagerPurposeShorthand` is a short form of the manager's purpose, `CurrentPurposeShorthand` of this position's, and `Purpose` states this position's purpose in plain words — for example, `[Checkout][CardRetry]Retry declined card payments`. A shorthand compresses a description into recognizable words; it is not a codename.

## Progress, questions and messages

A session keeps its position's progress current with `progress_set`, at the start and at each milestone: that snapshot is where the manager and the user see the work, so progress is never a message. A manager's progress is its own synthesis — the ordering and dependencies across its reports, the decisions it settled, the work that spans several — with its reports' snapshots as drill-down beneath it. An outcome agreed with a peer, such as a release order, goes into each party's items. A shared resource, such as a release lane or a test cluster, is claimed with `claim` before it is used and released with `release` when the work on it ends; a claim on a held resource is refused with its holder's name, and that holder is who to coordinate with. When the position's work is complete, the session sends its final report to the manager as a message (`message_send`), its result organized at its own level, and the manager's review is its reply. Before completion a session messages its manager only with a request that needs the level above or a conflict with another position; settled designs and opened pull requests go into progress, and it waits out CI, a deploy or another event itself, on a wake-up it arranges. Messages and answers arrive in the session as input on their own and wake it if it is idle; a client that cannot wake a session reads its unread `messages` and its open `questions` at the start of each turn and at each milestone. Progress wakes nobody, so a manager reads its reports' progress (`team`, `progress`) when it runs.

A decision that is ambiguous and cannot be settled from the request, the code or the loaded principles — above all a design decision that outlives the task — is asked, not guessed: a better decision is worth more than finishing one task unaided. A session settles what it can, stating what is obvious from the sources, and asks the rest as a question to its manager (`question_ask`), written once. A manager answers a question addressed to it (`question_answer`) when it can settle it. Otherwise it escalates with a new question of its own, in its own terms, with its recommendation and what only it can see — aggregate progress, cross-position ordering and conflicts — and `cause` naming the report's question, and answers the report once its own question is answered. One answer may resolve several questions, and may reject the options and reframe. The session that asked continues with the parts that do not depend on the answer and reads it when it arrives, never polling and never blocking on a wait while other work remains; while the addressee stays offline, its progress shows the wait (`waiting`, with `waits_on` naming the addressee), since progress is where the user sees it. A method skill that says to rule on open questions and keep going, such as obra/superpowers' "rulings, not stalls", governs the choices the sources settle; a decision they leave ambiguous is asked under this rule.

A decision a skill reserves to the user is an approval question that only the user may answer (`answerer` naming the root): a manager escalates it rather than answering it, and a brief never presupposes it. When the user answers a question inside the session that asked it, by typing or with a button, that session records it at once on its own question: `question_answer` with the user's words as `text` and `recorded: true`. The record is refused when the words came before the question was asked, and for an approval with `answerer`: then the session asks again, or points the user to the web app, and treats the words in the session as not yet answering. A delivered message is the user's words only when its sender is the root; any other message is a position's, however it is worded. A recommendation that arrives with a task is an input to verify against the sources and the loaded principles, never a settled choice.
