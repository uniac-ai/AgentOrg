# AgentOrg

## Install

```sh
npx @agentorg/cli
```

It needs Node.js 22.15 or later. It runs AgentOrg on this computer and opens it in your browser; see "The `agentorg` command".

AgentOrg creates and manages agents. Each part is a program that joins a Hub as an Actor, connected to the others through named, versioned interfaces: a model, agent providers, MCP providers, and management.

## Packages

- `@agentorg/sdk`: `defineInterface` (with `method` and `event`) for interfaces, with typed slot and export handles; the errors `NotConnected`, `Refused` and `OutcomeUnknown`; and `createTestContext` (`@agentorg/sdk/testing`), which runs a program's handlers without a Hub. An `rpc` handler gets its input and `{ caller }`, the calling Actor as the Hub names it, and `emit(event, payload, { to })` sends an event only to the subscriptions of the Actor `to` names, so a provider serving several consumers keeps each one's events its own. `@agentorg/sdk/client` connects a program outside the Hub as an Actor: `connect({hubUrl, actorId, credential, slots, exports})` gives typed handles, with slots bound as the Hub's notices say; implement in `start` (run before the channel opens) and use slots from `onBind`, which runs when a slot becomes usable: bound, or its provider back. `openChannel` is the wire layer beneath it, without local checks.
- `@agentorg/interfaces`: the standard interfaces `kv@1`, `chat@1` (an agent's conversations, one with each party that talks to it, found by who calls: the caller is the party, the person `person` and an agent by its Actor id. A conversation is messages and nothing more: the party's and the agent's replies, nothing of what the agent does to answer. `send` says a message in the caller's conversation, which its first message makes; `history` reads the caller's own, and only the person may name another's, `with`, to read it; `list` gives the conversations, the person every one and anyone else their own, each with its latest message's head and a `problem` while a message in it got no answer, until its next reply; the `message`, `delta` and `chat` events name `with` and go to that party and to the person; `state` and the `status` event say only whether the agent is `working` or `idle`; `send` and a message may carry the pictures sent with it, and a picture may be sent with no words), `llm.session@1` (stateless model inference, with function tools; a request longer than the model takes is refused `context_length`; a user message and a call's output may carry pictures; the reply's text, and the arguments of a call of a function marked `streamed`, stream as `delta` events, the latter naming the call), `account.login@1` (signing in to an outside account, driven by a person or a program), `tools@1` (a set of tools known only at run time, as one fixed contract; a call's result may carry pictures beside its text; a call may carry a `group`, a word of the caller's, and `stop` ends what a group's calls started and left running), `agent.settings@1` (what a running agent reads for its instructions and skills), `mcp.provider@1` and `agent.provider@1` (programs that make connections to MCP servers and agents; a creatable may declare a capability its agents hold of themselves, served by each agent's own `capability` and `tools`, which management records with no `from` and connects the person to as to a unit's), and `unit.provider@1` (a program that offers units of an agent's stack, each with its form as data, in which an option can be marked a caution, whether a stack holds it at most once, and what it gives an agent built from it: slots and skills for the agent's side, and, for the person's, the capability it builds, with its live surfaces and its views. A view is data: a host draws it, and a unit paints nothing. Its `skill` gives a file of a skill a unit comes with, and `shipped`, the sha256 of each text that file had in earlier versions the provider shipped), `capability@1` (something a built agent holds, as it stands now: whether it can be reached, which of its surfaces can be opened, a ticket to open one, and an event when a view's data changed; one Actor per capability exports it, and the person is connected to it when the agent is built, as to its conversations), and `agents@1`, `connections@1` and `skills@1` (what the person calls to manage them), and the Hub's management interfaces `hub.actors@1`, `hub.grants@1`, `hub.bindings@1`, `hub.exports@1` and `hub.audit@1`. A picture travels inside the message that has it: a media type a model reads (PNG, JPEG, GIF or WebP) and its bytes in base64, 500,000 characters at most, a number the 1 MiB frame sets, not what a model needs; a message carries eight at most. Whoever makes one fits it.
- `@agentorg/wire`: the channel: yamux streams, length-prefixed JSON frames, stream headers and transports.
- `@agentorg/hub`: the core. Its state, in `node:sqlite` in a private home: Actors, what each takes and offers, bindings and an audit trail. An Actor is a program that connects itself, with a credential. A binding is the grant, and it needs both ends: the export side (the provider, an Actor already bound to that export, or a manager) and the slot side (the consumer itself, or a manager). Through `hub.grants@1`, a caller with both ends binds; any other is refused. `hub.grants.expose({provider, export, to, as?})` exposes an `rpc` export to one Actor: a slot made on `to` at run time, typed by the export's interface and bound to it in one step, named `as` (one word of at most 48 characters) or by default the provider's name camelCased, `_` and the export's last part, made unique on `to` with `_2`, `_3`…. Its authority is a binding's, `to` being the consumer. Exposing the same export to the same Actor again gives its slot back. The slot goes with its binding: `unexpose({to, slot})`, `unbind`, the export no longer declared or declared as another interface, or either end closed; `hub.bindings` marks such a binding `exposed: true`. A manager is any Actor bound to `hub.bindings@1`. `hub.actors.create` can bind the new Actor's slots at once, with the creator's export side. The router serves it over WebSocket (`listen`), one yamux channel per Actor: a client's first stream is `hello` with its credential, then every `call` and `subscribe` stream is resolved through its binding, validated against the interface's JSON Schemas in both directions (ajv, 2020-12, in a pool of worker threads, each check under a time budget, since schemas come from Actors), forwarded to the provider with the caller named, and audited. An Actor learns which of its slots are bound from hello's result, then from a `slot` notice on each change. Every Actor's record in `hub.actors` says whether it is `connected`, holding a channel to the Hub now, and `hub.actors`' `changed` event names an Actor whose record may differ. A redeclaration that changes a bound name's interface keeps its bindings, each audited as `binding.keep`. A slot made by `expose` takes its export's new version, and goes if its export becomes another interface; any other binding whose ends now differ is `mismatched: true` in `hub.bindings`, and calls and subscriptions through it are refused `version_mismatch` until both declare the same. A binding still goes on unbind, when a name is no longer declared, or when either end closes. A refusal that names an Actor names it as "Name (id)", and says what the caller can do instead.
- `@agentorg/cli`: AgentOrg as one app. `agentorg` runs a Hub, the person's gateway and the shell on loopback; see "The app: the person's gateway".
- `@agentorg/mcp`: the built-in MCP provider, an external Actor exporting `unit.provider@1` as `provider`, and the only code that imports the MCP client (`@modelcontextprotocol/client`). `startMcpProvider({hubUrl, actorId, credential, dir})` runs it; its slot `actors` is bound to `hub.actors@1`. It offers two kinds: `url` attaches to a server over Streamable HTTP, sending `secrets.token` as a bearer token on every request (only over https or to this machine), and `command` starts a local server over stdio, with the basic environment and each of its `secrets` as an environment variable. Each connection joins the Hub as its own Actor exporting `tools@1` as `tools`: `list` and `call` go to the server, a tool's result comes back as text, with `failed` when the tool reported an error, and its image blocks as pictures, eight at most, together within one picture's cap and what the text leaves of the frame; each one left out, or of a kind a model doesn't read, is a line before the text saying so. `changed` fires when the server's tools change or it goes or comes back. A call's group, and a group's stop, reach the server only when whoever makes the connection names the server's own keys for them, as the computer's connection names AgentExec's; otherwise the group stays here and `stop` ends nothing. While a server is away `list` and `call` are refused `not_connected`, and the provider tries again after a backoff from 1 s doubling to 60 s (starting over after 10 minutes up). `create`'s `secrets` are write-only: the values cross once and go only to the provider's private `dir`, never into `params`, `target`, `detail`, status or a log (what a server prints is scrubbed of them). Each connection's Hub credential, parameters and secrets are kept in that folder, and connections rejoin at its next start. A server started by `command` is an ordinary process with the person's rights, outside the Hub's sandbox.
- `@agentorg/manager`: management, an external Actor exporting `agents@1`, `connections@1`, `skills@1` and, as `settings`, `agent.settings@1`. `startManager({hubUrl, actorId, credential, dir})` runs it; bound to `hub.actors@1`, `hub.grants@1` and `hub.bindings@1`, it is a manager. A provider of either sort is connected by exposing its export to it: the Hub's slots are the only list. It keeps what the Hub can't know, in its private `dir`: each connection's origin, each agent's provider, creatable, instructions and skills, what the agent holds (what its creatable declares it holds of itself, with no `from`, the person connected to the agent's own `capability` and `tools`, and held at the next pass for an agent made before; and for each applied unit that builds a capability: its id and title, its surfaces and views as worked out from the unit's description and the answers, the rows `apply` fixed, and the person's own slots to the capability's Actor and to each of its connections. Management makes those slots as the unit is applied, makes one again if the Hub drops it, and takes them off with the unit; `agents.get` gives all of it as `capabilities`, from the record alone), and the skills as `SKILL.md` folders. A skill a unit gives is copied there when an agent first gets it, and management keeps what it copied, each file's sha256. At its start, and when a unit provider connects, it brings each such skill up to the files its unit gives now, while the skill is as it was copied, and tells the agents that hold it. A skill with no copy kept, in a home from before copies were, is taken as one when each file is the text its provider serves now or one it shipped. A skill changed here is left as it is, logged once each start, and one the person or an agent adds under the same name is theirs and never brought up to date. Status is read when asked, what a connection is exposed to is the Hub's bindings, and `secrets` go straight to the provider. `agents.get` gives the agent's stack as the units providers made, and each skill and connection with the `instance` of the unit that gave it; one exposed to it, by `expose`, by management's own Skill, Connection or MCP unit on a connection there is, or by the agent that made it, is no unit's and has none. `agents.create` is all or none: the provider makes the agent, its `settings` are bound, its skills added (one whose name is here keeps the one here), each connection it needs made or picked and exposed under its slot, and its conversations exposed to the person; if a step fails, what this creation made is removed. The Hub keeps that exposure across an update of either end, and drops it when an agent stops offering its conversations; management makes it again each time an agent connects. An agent that manages its own reaches each agent it made, and, with "all", every other agent: that agent's conversations, exposed to it at `chat_<id>`, so it talks to it from itself; and the Work at `work_<id>` of each it made, while that agent is connected. The agent it made is told by its settings its maker's name and id, while its maker is here. An agent reads only its own instructions and skills, and only it hears that they changed. `agents.models` and `agents.setModel` pass to the agent's provider, as `start` and `stop` do; stopping an agent stops all of its work.
- `chatgpt`: the model, a program. It signs in with ChatGPT for the person's plan (`account.login@1`: OpenAI's OAuth for open-source apps, with dynamic registration, PKCE and a verified id_token; refresh tokens rotate, one refresh at a time) and serves `llm.session@1` on that plan through the Responses API, streamed and stored nowhere at OpenAI. A person's pictures go as image parts of their message, and a call's as parts of its output, each as a data URL. A model's reasoning before a call comes back from OpenAI sealed, since nothing is stored there. It is kept here in memory, by the Actor that asked and by the call, and put back before that call in that Actor's later requests until a user message follows it, so the model goes on from it through a turn. It is never given to a caller; an Actor's oldest goes once 400,000 characters are kept for it, and all of it at a restart or when the sign-in changes. The tokens never leave it: never in a reply, an event, a log or a refusal. It never uses an API key or API billing: a usage limit is refused `usage_limit`, with where to manage it. A request longer than the model takes is refused `context_length`. A response whose failure passes is asked for again, three times at most, before the failure is the answer: OpenAI couldn't be reached, said to try again later, its server failed or was overloaded (HTTP 408 or any 5xx, or its codes for those), it ended the stream with an error that has no code, or the stream broke off before any text of it, or any arguments of a streamed function's call, was written; a call of any other function streams nothing and doesn't stop a try. Each wait doubles from a second, or is the one OpenAI asked for when that is longer, up to a minute; past a minute, or once a try would begin more than two minutes after the first, the failure is the answer. A usage limit, an account that isn't eligible, a request longer than the model takes and a request OpenAI won't take are never asked again, nor is a response once text of it, or of a streamed function's arguments, has been streamed, since those words may be with their reader; a cancel ends a wait. The one exception: a request that had reasoning put back in it, and that OpenAI wouldn't take as it is with no words of its own here (a 400, a 422, or an error inside the stream before any text or streamed arguments), is made once more without it, and that reasoning is not sent again; if its error had no code, it then gets the tries above. An error inside the stream is read from the event's own fields and any nested in its `error`, which take their place. One with no code is logged as an error by its event's type and its fields' names (twenty at most, a name that could be a token shown as `…`), or, when the stream ended with no error at all, its response's; never their values. A failure with no words of its own here ends with what OpenAI said of it, cut short: nothing of a message about a credential or of a reply that refuses the sign-in, and no run long enough to be a token. `startChatGPT({hubUrl, actorId, credential, dir})` runs it as an Actor exporting `login` and `session` with no slots at all: the sign-in is in `sign-in.json` in its private `dir` (mode 0600, written through before a change is acknowledged, since a rotated refresh token can't be had again), and it reaches OpenAI over the network directly, https only, with redirects returned as they are. Its tests run against an in-process fake of OpenAI, so none reaches OpenAI.
- `@agentorg/looper`: an agent's loops, knowing nothing of what hosts them. `createLooper` is given a model client, the tools a request may call, a store for its records and where to say what it does, each as a plain type of its own, and takes a message with the name of the thread it came in on. What answers is a piece of work, with a loop of its own, or, when a message needs no work, the main loop. A turn of a piece of work sends the work's messages and the tools to the model, runs what the model calls, and goes on until a request calls nothing or the turn is stopped, however many calls that takes. What a request sends of a conversation fits in about a megabyte, what the Hub carries in one piece, less the request's instructions, its tools and the pictures its conversation holds (500,000 characters at most), and never less than 400,000 bytes. With no pictures that is a quarter of a million tokens or so, more for code; a model that takes fewer refuses the request for its length, which is handled next. A piece of work whose conversation goes over that room, once its turn has sent something or run a call of its tools (a request that only decides whether to take what the turn was given is cut to fit instead, since handing it back would make a summary for nothing), or whose request the model refuses for its length (the refusal code `context_length`), first has its earlier steps summarized by its own model, as pi does (adapted from pi, MIT; see the package's NOTICE), in a request with pi's prompts and no tools. It summarizes all the work has read since its last summary except the newest 80,000 bytes or so, cut between entries so a call stays with its output; the part of an exchange before the cut, when the cut falls inside one, is summarized apart and set after the rest. The model is given that part of the conversation as text, each call's arguments and output cut at 2,000 characters, in pieces of at most 160,000 characters: past one piece, it is summarized a piece at a time, each request updating the summary, eight pieces at most, and past those the oldest are left out and the text says so. Each later summary updates the one before. The summary, at most 16,000 characters (past that, what came before the cut exchange gives way first), with the files the host's `files` says the calls read and changed (each list its newest within 900 characters), is kept as an entry of the work's record, which the retention cap never deletes, and nothing of the record is deleted for it; the work's Activity shows one line, `Earlier steps summarized to continue.`. From then on the model is sent the message the work opened with and the messages the summary covers that are still to answer, so it can answer them by number; then the summary, as a user message; then all after it, word for word. A summary is made only when at least 100,000 bytes would go into it, beside the opening message and those still to answer, which are sent anyway; after a length refusal any amount will do, and the request is asked once more. When summarizing fails, the turn takes the cut below and summarizes nothing more until its next turn. What is still over the room is cut to fit, oldest first: what calls before the latest exchange (a message from the person and all done until the next) were given and gave back, each call keeping an output; then whole exchanges, except the message the work opened with and the latest two, one line in their place naming the messages it stands between; last, the latest exchange's calls. What was said in exchanges that stay is never cut. The cut grows 100,000 bytes at a time, so requests between two cuts begin alike. Pictures aren't counted as words: they have the room a request of about a megabyte leaves beside the conversation as it is sent, its instructions and its tools, 500,000 characters at most. First go those the person sent with the messages the turn is answering, then those its calls gave, then the person's older ones as they fit, each the newest first; each one left out is said where it was, as `(A picture, left out.)`. A call's pictures are kept only while a request can give them: once newer ones of its turn fill that budget, or its turn is over, they are left out of the record too, so a turn of many screenshots doesn't fill a thread. The main loop is given the person's pictures of the messages it is told, the same way. A call's arguments, other than a said `send`'s, are kept to 16 KiB: past that, arguments that are JSON stay JSON, every string in them longer than one length cut to it, the longest length that fits, each ending with how many more characters it had, so a path or a name stays whole; arguments that aren't JSON, or that are still over with every string cut, are kept as a note that they were left out. A thread may be followed by several pieces of work. A message in a thread that work follows is given, in code, to each piece of work that follows it and is in a turn, running or waiting for a place; with none in a turn, to the one last active there (the last to answer there, or to be given a message there), which starts a turn. With one it is that work's to keep; with several it is kept once, naming each, and each takes it in its own order. One in a thread nothing follows is recorded and said at once, and the main loop decides on the thread: one model request with one function, `route`, and no other tool. It is told the work there is, each piece by id and title, whether it is in a turn or at rest, and whether its last turn failed, and the head of what it last said (twelve at most: those in a turn, then the latest at rest), and then the thread as a conversation (its newest eight messages, the first 4,000 characters of each). It says what came in is new work, with a title, or points at work there is, which then follows that thread too and, if at rest, starts a turn; or it answers itself, in text, when the message needs no work: that text is kept and said as the thread's reply, streamed as it is written, and the thread stays no work's, so its next message is decided the same way. Text beside a call is said too, and what came in is placed all the same, unless the call names work to stop. It is told to give a message to work only when the message points at that work explicitly, and to answer only what needs no tools and never to promise work. It speaks as whoever hosts it says (`voice`), told after its own words. A message said in a thread whose speaker the host names (`speaker`, none for the person) starts, after its number, with who it is from, for its worker and the main loop. It decides for one thread at a time, on all that waits in the thread, and keeps nothing between decisions but what the thread holds; an answer that says and calls nothing, or places with no work it was told of, starts new work. When a turn ends, the work's record is given the time, the head of what it last said, and whether the turn failed. What a worker's request writes is kept for its work and said in no thread, nor streamed. `send` is offered as streamed, so what it says streams as the model writes it, into the thread of the message it names and under the id its reply will have, once that message's number has been read: text written before the number waits for it, and a send naming no message this work can answer streams nothing. Pieces of a send the model gives up as it writes it are completed by no message. A reply an earlier version kept is read by the model as a `send` to the message before it, so it is not taken for words that were never said. A worker's request is what its host gives, and after it the looper's own: which work this is, by its title; the titles of the other work in the conversations it follows, in the order it began (by the first message each holds), the newest twelve, and that a message about what one of them did or decided is not this work's, though it says "you", and to hand such a message back, naming the one it is about, rather than answer that this work didn't do it; each of the person's messages starting with its number in that work's order; and two functions beside the host's tools. `send` is the only way a worker says anything to the person: it says its text in the thread of the message whose number it names, as the reply to that message, and answers it. It is refused, and the worker told so, for a number the work has no message at, one it handed back, or one in a thread it has left, and for empty text. A worker may send more than once, to several messages, and goes on after; the call is kept as that reply, and like what was said its words are never cut to fit. A reply any piece of work sends answers its message for every piece of work it was given to. A turn that ends by itself says of each message it took that was neither answered nor handed back that it went unanswered: kept on the message, and its thread told `not_answered` before the work is idle, once for each thread. A stopped or failed turn leaves its messages open, and a later send may still answer them. What a worker's calls did is its work's too, and said in no thread. `hand_back` says a message is not this work's, with why, once per message. Its call is kept for the worker to read and shown to nobody, and a request that only handed messages back ends its turn, when the turn has sent and called nothing else (words it only wrote are not acting) and nothing else said to that work is unanswered: a worker at a task goes on with it. With `leave` the work is given nothing more from the thread the message was said in, unless it began there; it still reads what it holds of it, and takes and writes nothing more there; a message there that it was given and had not yet taken, it hands back unread by leaving, and if the store refuses that it has not left. A message that every piece of work it was given to has handed back is the main loop's to decide: it is put the work there is, less the work that returned it, then the thread as a conversation up to that message, then which work returned it and why. It answers, which is kept as no work's and read by none; or gives it to work it is told of, which then follows that thread too; or starts new work, which has the thread's name as its id unless the thread has work already or holds a message that came back, and then an id of its own. Each decision on what came back is one write: the answer names the messages it answers, and a message given to work names that work, new work with its title, before anything else is kept. A thread is marked before a message in it is given to several pieces of work or says it was handed back; the mark stands while any of that is under way, and goes in one place, when nothing waits there as the store has it: a message a piece of work is taking still waits until that is kept. A piece of work is marked before anything of a turn it starts is kept, with the place the turn starts after. So a looper that goes in the middle leaves the next to finish what was decided and give what was said, and to decide nothing twice. Nothing but a worker leaving takes work off a thread, so a thread used for many things gathers followers, but a message there costs a model request only for each in a turn, or, with none, for the one last active, and one more for the main loop if that one hands it back. One piece of work is stopped by saying so. The main loop may answer a message in a thread nothing follows by stopping work in a turn that the message asks to stop, when exactly one fits: it calls `route` with `stop`, which places nothing, and what it wrote is that thread's answer, or, when it wrote nothing, `Stopped.` if a turn was cut and `Nothing was stopped.` if not. Only that thread is told, and it stays no work's. And a message said in a thread that work follows, which joins a turn of one or more of those pieces of work, is, beside those turns taking it, put to the main loop once with the pieces of work whose turn it joined, less any whose turn has ended by then: one more request, in the looper's own words without `voice`, in which it may only stop one of those turns. When several are in a turn and the message asks to stop without saying which, it says which are in a turn, and that is kept in the thread as no work's. These requests take their place among the decisions, one at a time; a message that starts a turn makes none, nor does one said before the work followed its thread, which the work takes with the thread. Stopping cuts the turn the main loop was told of, as the looper's own stop does for all, and no turn that began after it: a call already running finishes and its result is kept, and the work is at rest, not failed. A turn's calls carry one group, and a stop, unlike a close, asks the host's `stopGroup` to end what they left running: at the stop, and again when a call that was running comes back. Where the message joined the turn, what the main loop says of stopping it is kept at once in that thread as the work's own, and the work reads it after whatever the stopped turn still writes; if the store refuses it, the turn is cut all the same and the thread is told it failed. A message said to work whose stopped turn is still writing (a running call's result, or a reply being kept) is kept and said at once, as part of that turn's tail: the turn it starts takes over the stopped turn's place and shows as running, and makes its first request once the stopped turn has written what it will, so the model reads that call's result before the message. What the main loop was to hear of is not kept: a stop, a close or a restart before it has answered drops it, and the worker has the message all the same. A message is kept once, in the thread it is shown in; a piece of work reads its own across the threads it follows, in the order it took them, and what comes of a model request is written in the thread of the newest message that request read and the work has not handed back; what a request writes beside a hand-back is written where that request began. Turns of different pieces of work run side by side, four at once, and one more that only work that has already done something may take; a turn past that waits for a place, and while such work keeps five turns running new work goes on waiting. Sixteen turns may wait; past that a message that would start a turn is refused `busy`, or, when the main loop had it, kept and told to have failed `busy`. The main loop takes no place. A message said to work whose turn is running or waiting is recorded and said at once, and that turn takes it at its next model request. A turn that fails tells every thread it had taken a message in. A piece of work is marked in the store while a turn of it hasn't ended, and a thread while it holds messages that wait, for the main loop to decide on or for work to take: `resume` goes on, once, with each turn of which something was kept (its work holds a message said to it past the place its mark names; a turn stopped while it started has no mark, a stop takes off the mark of one that couldn't go on when it was looked for, one the looper's closing cut keeps it, and a turn that starts while a mark still stands for an earlier one leaves that mark as it is) and each decision that was cut off by a looper closing or going without closing, and the model of a turn that goes on is told to check what is already done. A thread the main loop answered, couldn't place, or was stopped over, waits for its next message, and the main loop is put what the thread holds. Stopped, it cuts every turn and the main loop, and takes no message until it is started. `works` lists its pieces of work, most recently active first, or those last active before a given one, each working, idle or stopped, with its latest entries, a call running now last; `entries` pages back through one's; the host is told `worked` when either may answer differently. It imports no other package of this repository, and a test of its own fails if a file under its `src` does.
- `assistant`: the agent engine and the bundled agent provider. The engine binds the looper to one agent: a conversation is a thread, one with each party that calls it, the model and the tools are the agent's slots, and the records go where the agent's are kept. A message from anyone other than the person is shown to its worker and the main loop with who it is from, by Actor id. In another party's conversation the main loop is told only of the work that follows it, and routes into and stops only that; in the person's, all of the agent's work. An agent talks from itself to each agent whose conversations are exposed to it: it is offered `agents__send` (a message, naming the agent by its id) and `agents__read` (its conversation with that agent, a page at a time, its oldest messages left out to fit what a loop takes whole; whether the agent is working; and a problem if a message got no answer). Saying stop in a conversation stops the turn of the one piece of work there that it asks to stop, and no other's; the agent's own Stop stops all. A stopped turn's calls carry one group, and each tools slot is asked to stop it, so the commands the turn started on the agent's computer end; a turn that ends by itself leaves them running, as does the app closing. A message in a conversation no work follows is read by the agent's main loop. It answers a plain message itself, as the agent, and that conversation stays no work's; or it starts new work for it, or, when the message points at work there is, gives it to that work, which reads it with all it holds. A piece of work says something only by sending it, as the reply to one message, in that message's conversation, where it streams as the model writes it; what it writes without sending, and what its calls do, are its work's and shown in no conversation. It follows the conversation of the newest message it has read from then on, beside any other work that does: a message there reaches each that is in a turn, or, with none, the one last active there, and a worker hands back what is not its work's, for the main loop to place. The main loop's request is the looper's own words, then the agent's own instructions, which it speaks as, and one function: none of the agent's skills or tools. The request that only hears of a message said to work in a turn has the looper's words alone. So an agent works on several things at once, as the looper's places allow. `startAgentProvider` runs an external Actor exporting `agent.provider@1` as `provider`, which offers one creatable, Assistant. Each agent is its own Actor on its own channel in that process, exporting `chat@1`, with the model behind `model: llm.session@1`, instructions and skills from an optional `settings: agent.settings@1`, and tools from each `tools@1` slot exposed to it. It also serves its Work, which the Assistant creatable declares it holds of itself: `capability@1` as `capability`, and as `tools` a `tools@1` with one tool, `work`, which an `activity` view and another agent both call. With no arguments `work` answers the agent's pieces of work, most recently active first (six at most), each working, idle or stopped, with its three latest entries: a call with whether it is running or how it ended, words its worker wrote and didn't send, or a line of its own. Its `more` says whether others remain; `before` with the last one's id gives them. With `work` it answers that piece of work's entries before `before`, twenty at most. Each text an entry carries is cut at 2,000 characters, and an answer leaves out its oldest entries to stay within 28,000, so another agent's loop takes it whole. It answers while the agent is stopped too, its state is reachable whenever the agent is on its channel, and its `changed` event names the `activity` view when a turn begins, a call begins or ends, or something of a piece of work is kept. Its conversations and model choice stay in the provider's private folder; the model is chosen through the provider's `models` and `setModel`, which name the agent. The agent is `working` while its main loop decides or any work's turn runs or waits. A stopped agent stays on its channel and runs no turn: its conversations can still be read, and a message is refused `busy`. A message sent in a conversation is recorded and shown at once, with any pictures sent with it, which the model reads; a turn running for work that follows the conversation takes it at its next model request. A tool's pictures reach the model with its call's output. When a piece of work's earlier steps are summarized, the summary lists the files its calls read and changed, by the tools' names: a call of any slot's `read` is taken as reading the file its `path` names, and one of its `edit` as changing it, as the computer's file tools do. A message that gets no answer leaves its conversation with a `problem` (`not_answered` when its work's turn ended without a reply to it), until that conversation's next reply, and a message sent after it is read with what went unanswered. An agent that had several chats keeps one conversation when it starts on this version: the person's chat last written in becomes their conversation, and every other chat is deleted, those another agent started too, with the pieces of work that followed only those; one line in its log counts them. A turn that a restart cut off goes on once when the agent is back, its work keeping one line that says so, shown in no conversation, and its model told to check what is already done; one that ended, failed or was stopped doesn't.

## Errors

- `NotConnected`: the slot is unbound, or the export is no longer declared.
- `Refused` with code `invalid`: the caller's input broke the interface's schema. Nothing ran.
- `Refused` with code `bad_output`: the provider ran, and its reply or event broke the contract. The call may have had its effect; read state before retrying.
- `Refused` with code `unimplemented`: the export has no handler for that method yet.
- `OutcomeUnknown`: the channel dropped mid-call. Read state before retrying.

## The `agentorg` command

`@agentorg/cli` provides `agentorg`.

- **`agentorg`**, with no command, runs AgentOrg: a Hub in its home, the person's gateway and the shell, on `127.0.0.1` (`--port N`; else the port a browser is still signed in at, when it can have it; else any free port). It opens the browser already signed in, and prints only its address, never a sign-in code. `--no-open` doesn't open a browser. The code is in the address it hands the system's opener; on Linux, other local users can see that program's arguments for the moment it runs, and the code works for 60 s.
- **`agentorg --version`** prints the version. An option the command doesn't know is refused with the usage (exit 2); it never starts the app.
- **`agentorg open`** signs a browser in to the running app again.
- **`agentorg hub [--port N]`** runs a bare Hub in its home, without the gateway or the shell, serving WebSocket on loopback, and writes the address to `<home>/url`.
- **The person's commands**, one per hub method:
  - `agentorg actors|bindings|exports|audit`;
  - `agentorg bind <consumer.slot> <provider.export>`;
  - `agentorg call <slot> <method> [json]`.

  While the app runs, they go through it, with the CLI's token in `<home>/cli-token`. Otherwise they connect as the person with `<home>/person-credential`, and never take over a channel something else holds (hello's `replace: false`).
- **The home** is `--home`, else `$AGENTORG_HUB_HOME`, else `$XDG_DATA_HOME/agentorg` when `XDG_DATA_HOME` is an absolute path, else `~/.local/share/agentorg`, on Linux and macOS alike.
- **Output:** results are JSON on stdout. A refusal exits 1 with its reason on stderr, and a usage mistake exits 2.

`@agentorg/sdk`'s own bin is `agentorg-sdk`, with the same commands but no app.

## Try it

From a clone, after `npm ci` and `npm run build`, with `agentorg` being `node packages/app/dist/src/cli.js`:

1. **Run the app:** `agentorg`. It prints its address and opens the shell in the browser, already signed in; `agentorg open` signs a browser in again.
2. **See what can be created:** `agentorg call agents creatable`. It lists the Assistant, with the id of the provider offering it.
3. **Create an agent:**

   ```sh
   agentorg call agents create '{"stack":{"base":{"provider":"<provider>","creatable":"assistant"},"units":[]},"name":"Scout"}'
   ```
4. **Open it in the shell,** sign in to ChatGPT there, and chat with it.

To run the tests, install the browser they drive once, with `npx playwright install --only-shell chromium`, then `npm test`. The shell's, the connector's and the app's tests use Playwright's headless shell, never a browser installed on the machine.

## The app: the person's gateway

`agentorg` runs the person's Actor as the app's gateway: its single running instance, holding the person's one channel to the Hub, in this process. Browser tabs and the CLI are the person's UIs, not channels: they reach the gateway, not the Hub.

- **Sign-in:** the browser opens `/signin#<code>`. The code is one-time, lasts 60 s, and sits in the fragment, which no request carries; the page drops it from the address at once. It trades the code, with a same-origin POST, for a session, which it keeps in the shell origin's `localStorage`. That's no cookie, because browsers send a `127.0.0.1` cookie to every port there; storage is the origin's alone, port included. The gateway keeps only a hash of each session, in `<home>/sessions.json` (mode 0600), so a tab is still signed in when the app starts again at the same address, which a plain `agentorg` takes again when it can. At another address (that port taken, or another asked for) the kept sessions are dropped as it starts. A session ends only when 256 newer ones have been given. A one-time code and the CLI's token don't outlast the app.
- **`/api`:** one WebSocket per tab, with the same calls a channel carries, as JSON:
  - `{id, op: "call", slot, method, input}` is answered `{id, result}` or `{id, error}`;
  - `{sub, op: "subscribe", slot, event}` gets `{sub, payload}` per event, and `{sub, end: true}` when it ends; `{sub, op: "unsubscribe"}` stops it.

  A socket holds 256 subscriptions and 64 calls in flight at most (past it, `busy`). A tab's socket must come from the gateway's own `Origin`, and its first message must be `{op: "hello", session}` with a live session, answered `{op: "hello"}`; otherwise it's closed with code 4401, and the tab signs in again. The CLI gets in with the token in `<home>/cli-token` (0600, new at each start) as a bearer. The gateway answers only to `127.0.0.1:<port>` in `Host`, so a page that rebinds DNS to loopback gets nothing.
- **What the calls reach:** the person's slots: `actors`, `bindings`, `grants`, `exports`, `audit`, and the four the first run binds: `login` (`account.login@1`, the model's sign-in), `agents`, `connections` and `skills`. A slot exposed to the person at run time, such as an agent's `chat@1`, is reached under its name from `bindings.list`. `store` answers from the app's own notes, `<home>/app-notes.json`.
- **The first run,** at every start, beside serving (`startPrograms` in `src/programs.ts`; `app.firstRun` settles with what it started): ChatGPT, the agent provider, the MCP provider and management, each an Actor of its own run in this process, with a private folder and a credential under `<home>/programs`. Each provider is connected by exposing its export to management. Each step reads what is there first, so a restart, or a first run that stopped half way, makes nothing twice. Any package Actor an earlier release left is closed before the Hub opens, and its files are left where they are. The app's log is standard error, a line each, beginning with its time in UTC: what its programs log as an error, a step of the first run that didn't work, and a program that didn't stop.
- **`/oauth/chatgpt`:** where ChatGPT sends the browser back after sign-in. It takes `GET` only and hands the whole address, which holds the sign-in's code, to `login.complete`. Then it sends the tab on (303) to `/oauth/chatgpt?result=<outcome>`, so the code leaves the tab's address and history; that page says how it went and links back to the shell. The code is never logged or shown, and no referrer is sent.
- **The app's own pages** carry a policy of their own: scripts and styles from the app only, framed by nothing.
- **The shell,** `@agentorg/shell`, is what the gateway serves at `/`: one socket to `/api`, and nothing it decides on its own. Its pages are fixed: Agents, one agent, Chat, Skills, MCP connections and Settings, each reading the person's slots and what is exposed to the person.
