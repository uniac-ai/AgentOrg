0.0.42 is on npm under the `next` tag, as 0.0.41 was: `npm install -g @agentorg/cli@next`. `latest` stays 0.0.15. It pins AgentComputer 0.0.41, as 0.0.41 did.

## What you meet

- **Nothing changes on the page or in the CLI's commands.**
- **Agents are told and offered what they were.** They read skills and use control as before. They are offered the same functions, with the same names, descriptions and words. The saved copies of what agents are told and offered, one of them an agent holding control, are the same byte for byte.
- **Two answers read a little differently:**
  - What an agent holding control is made of has one part more, `offered` ("What it can mount"). It tells the agent what it can mount, which its control told it before. `capability_list` and `agentorg call agents get` show it.
  - If management goes away in the middle of a control call, the agent is told "control is not connected." where it was told "agents is not connected.".

## What changed underneath

- **An agent asks management nothing.** Management gives the program that runs an agent a list of what is mounted on it, and the agent works from the last list it was given.
  - The list travels in the agent provider contract, `agent.provider@2`, which adds `mounted`.
  - What a skill always says, its `ALWAYS.md`, comes with the list. An agent reads a skill's files through a tool management gives it.
  - An agent's control is tools management gives it, and management decides what each call may do: on the agent itself and on the agents it made. What it can mount comes with its list.
  - The old settings contract, `agent.settings@1` and `@2`, is removed. `agents@1` no longer answers an agent; the person uses it as before.
- **Starting together:**
  - Management keeps giving an agent its list until the agent's provider takes it.
  - A message sent before an agent has its first list, as at a start, waits for it. The agent shows as working, and Stop ends the wait.
  - The app connects the agent provider to management before management starts. So an upgraded home's agents aren't reported down at its first start.

## For development

- **The code is kept in modules, by import:** the person's (the shell and the person's CLI), the coordinator (the Hub, management, the MCP provider and the gateway), the agent provider (the assistant, the looper, the ChatGPT account and memory) and the capability (the computer). They share a core: wire, sdk and interfaces. The app that puts them together may take from each.
  - CI fails on an import across modules. The few crossings there are today are listed in `scripts/modules.json`, and the list may only shrink.
  - The folders follow: `packages/coordinator/`, `packages/agent-provider/` and `packages/capability/`. Every package keeps its name, and the moves left the packed `@agentorg/cli` the same.
- **The interfaces package is sorted** into five sets, each the contracts one side answers, and a base. A test checks every interface's hash and exported name, so a move can't change a contract unseen.
- **A saved copy of what an agent holding control is told and offered** joins the others.

## What you need to do

- **A home from 0.0.41:** nothing. At its first start on 0.0.42, its agents run, bound as they were, but for two bindings:
  - where an agent was bound to management's settings, it is bound to management's skill tools;
  - an agent with an AgentOrg control unit no longer has `agents@1` beside its control tools.
- **The list of what is mounted on each agent** is kept in memory only, and given again at each start.
- **A home from 0.0.40 or earlier, back to 0.0.5's:** as when 0.0.41 opened such a home, then as a home from 0.0.41.
- **Going back:**
  - **`agentorg update --back`** puts back 0.0.41, with the home as it was just before the update, the Hub's store included. Everything changed since that update is lost.
  - **Going back to 0.0.41 with npm alone** keeps the home as 0.0.42 changed it. 0.0.41 opens it, and its agents start and answer. But 0.0.41 binds an agent to management's settings only when it makes the agent. So each agent made before going back is told only the Assistant's own words: none of its own instructions, its skills, or what is mounted on it, such as memory or control. Agents made after going back are whole. That is from the code, not run. Go back with `agentorg update --back` instead.
- **The install line** still installs nothing while no signed Mac app is published, and `agentorg update` stops the same way.

## Not run on a Mac

As before, the service under the real launchd, the install line, `agentorg update`, `agentorg update --back` and `agentorg uninstall` were checked with stand-ins: the release's Mac check runs them only for a release that carries a Mac app, and none has yet. Going back to 0.0.41 with npm alone wasn't run anywhere.
